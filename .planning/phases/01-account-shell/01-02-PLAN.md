- **D-02 — Email whitelist в БД для анти-рандом (resolved 2026-XX-XX, plan 01-02).** Только email из таблицы `allowed_emails` может запросить magic link. UX поведение для не-whitelisted email: **silent drop** (security best practice).
  - Whitelisted email: signIn callback returns true → NextAuth генерирует token → Resend отправляет письмо → user видит на `/login?sent=1` баннер «Если ваш email в нашем списке, мы отправили ссылку. Проверьте почту.»
  - Non-whitelisted email: signIn callback returns false → NextAuth НЕ отправляет письмо → user редиректится на ТУ ЖЕ страницу `/login?sent=1` с тем же баннером (НЕ на `/no-access`).
  - Rationale: разные ответы для whitelisted vs non-whitelisted leak whitelist content via timing/redirect difference (user enumeration attack — OWASP ASVS V3.2). Single response = attacker не может определить, существует ли email в системе.
  - `/no-access` остаётся как landing для просроченных/невалидных magic link click'ов (где attacker уже имеет token и пытается его использовать после expiry — там разница ответов уже не важна, наоборот, user должен понять что link expired).
  - Admin вручную добавляет email через seed-скрипт / прямой SQL (полный admin UI — Phase 2 / ACC-04).
  - **Note:** This resolves research assumption A1. Original CONTEXT D-02 wording said "redirect на /no-access" for non-whitelisted; the security-best-practice silent drop is a refinement, not a contradiction (D-02 rationale "не давать информацию о существующих юзерах" is preserved more strongly).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Klassio dev machine → Supabase API | DATABASE_URL passes credentials in plaintext over TLS. URL contains password. |
| Klassio dev machine → Resend API | AUTH_RESEND_KEY grants ability to send mail from any verified domain on the account. |
| `.env.local` (filesystem) | Contains all production-equivalent secrets. Read by anyone with shell access to the machine. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Information Disclosure | `/login` response (redirect target / banner content) | mitigate | **Resolved here in CONTEXT.md D-02 update.** Single response (`/login?sent=1`) for both whitelisted and non-whitelisted emails defeats user enumeration. ASVS V3.2.1 (no info leakage in auth responses). Implementation lands in Plan 04. |
| T-01-09 | Information Disclosure | `.env.local` containing DATABASE_URL password + AUTH_RESEND_KEY | mitigate | `.gitignore` (Plan 01) covers `.env*.local`. Vercel env vars use Vercel's encrypted env store (Plan 06 sets them). Password manager stores Supabase DB password. Never commit `.env.local`. ASVS V14.3.2. |
| T-01-10 | Spoofing | Resend API key compromise (e.g., leaked from `.env.local` if machine compromised) | accept | Free-tier Resend account: blast radius limited to 3000 emails/mo, no payment method attached. If compromised, regenerate via dashboard. ASVS V14.3 (rotate quickly). Risk accepted: hardware token / KMS for secrets is out of v1 scope. |
| T-01-11 | Tampering | User chooses Vercel Hobby + ships paid product → ToS violation suspends deployment mid-Phase-4 | mitigate | Decision recorded in COSTS.md tracking + (if hobby) STATE.md TODO. Phase 4 execute-plan picks up TODO and prompts upgrade before deploy. RESEARCH Pitfall 9. |
