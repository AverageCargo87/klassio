## Q1: Что такое "задача" в тренажёре?

Сейчас в `sample-column-addition.json` 5 задач разного типа (numeric, single-choice, matching). Это **набор**? Поток? Игра?

**Подварианты:**
- **a)** Линейный поток: «реши задачу 1 → 2 → 3 → ...» с прогресс-баром. Урок = пройти все задачи.
- **b)** Параллельный пул: ребёнок видит все 10 задач сразу, решает в любом порядке.
- **c)** Адаптивный: учитель (Nataly) сам решает какую задачу подсунуть следующей в зависимости от того что обсуждается.

В реализации (c) — тренажёр получается **управляемый агентом**, что симметрично с Phase 8 идеей про доску.

## Q2: Где тренажёр живёт визуально?

Сейчас (Phase 6.5 layout) тренажёр — bottom-right, занимает остаток после VoicePanel + TranscriptPanel. На laptop это ~30% правой колонки = очень мало для решения задач.

User озвучил намерение **«доску уменьшить, тренажёр увеличить»**.

**Подварианты:**
- **a)** Сделать тренажёр **главной** панелью (доминирующая центральная зона), доска — побочная (выдвижная или маленькая).
- **b)** Tabbed-layout: одна большая центральная зона переключается между доской и тренажёром (учитель команд `show_board` / `show_trainer`).
- **c)** Tracked-by-context: layout автоматически меняется в зависимости от того что сейчас делается (объяснение → доска впереди; задачи → тренажёр впереди).
- **d)** Оставить три панели но переразмерить: 30% доска / 50% тренажёр / 20% voice+transcript+avatar.

## Q3: Какой функционал доступен из тренажёра?

Сейчас Phase 7 поддерживает:
- Numeric input — ребёнок вводит число
- Single choice — клик по варианту
- Matching — перетащить пары

Что **ещё** нужно для покрытия программы 5 класса?
- Drag-and-drop drawing на координатной сетке (для прямоугольников/периметра)?
- Дробное представление (визуальная плитка/круг)?
- Drag-and-drop столбикового сложения (расставь цифры по разрядам)?
- Свободный текстовый ввод (для словесных задач)?
- Multi-step problems (несколько подзадач внутри одной задачи)?

## Q4: Кто отвечает за прогресс?

Сейчас тренажёр fire-and-forget — emit'ит answer_submitted, никто не **отслеживает** правильно/неправильно последовательно.

**Подварианты:**
- **a)** Тренажёр сам ведёт state: "у меня 10 задач, решены 3, осталось 7", показывает прогресс-бар.
- **b)** Агент (Nataly) ведёт state — она помнит "мы уже разобрали units, теперь tens". Тренажёр — пассивный displayer.
- **c)** Pedagogical LLM (server-side) ведёт state — но это **возврат к полной Phase 8**, которую мы решили заменить на 8-mini.

## Q5: Реакция учителя на действия ребёнка в тренажёре

Сейчас тренажёр-events `trainer:answer_submitted` существуют, но **никто их не слушает**. Не передаются в Nataly.

В Phase 8 они должны идти агенту через `sendContextualUpdate`. Какая модель события?

**Подварианты:**
- **a)** Каждое нажатие → апдейт ("ребёнок ответил 9 правильно"). Агент сам решает реагировать или нет. Risk: спам контекста, агент перегрет, дороже.
- **b)** Только значимые события: правильный/неправильный ответ, hint-opened, idle_15s. Не каждое keystroke. Это более reasonable.
- **c)** Агент сам спрашивает тренажёр через client tool: «get_current_task_state()». Pull, не push. Чище но медленнее реакция.

## Q6: «Я объясню тебе сложение в столбик» — где это? на доске или в тренажёре?

Пример сценария: ребёнок открыл урок «Сложение в столбик», агент здоровается, спрашивает имя, потом говорит «давай разберём 245 + 874».

**Тогда что нужно показать?**
- **a)** Анимацию сложения **на доске** + параллельно задача в тренажёре «реши 358+467 сам».
- **b)** Всё **в тренажёре** — там пошаговый воркшоп с интерактивными слотами (сначала единицы, потом десятки, ...).
- **c)** Гибрид: доска для введения, тренажёр для практики.

Это связано с Q2 (layout) и Q3 (функционал тренажёра).

## Q7: Структура урока 45 минут

Нужно ли тренажёру понимать «фаза урока»?

**Подварианты:**
- **a)** Нет. Тренажёр — это просто набор задач, агент решает когда какую показать.
- **b)** Да. Тренажёр имеет explicit phase: warmup → main_topic → practice → review. Прогресс-бар по фазам, не по задачам.
