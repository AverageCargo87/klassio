## Техника реализма — код (three r160)

### 0. Стартовый блок — то, что даёт больше всего за 5 минут

```js
const renderer = new THREE.WebGLRenderer({ antialias: true, powerPreference: 'high-performance' });
renderer.setPixelRatio(Math.min(devicePixelRatio, 2));      // на 4K-ноуте DPR 2.5–3 съест 2/3 fps ни за что
renderer.outputColorSpace = THREE.SRGBColorSpace;            // дефолт, но пусть явно
renderer.toneMapping = THREE.ACESFilmicToneMapping;          // ⚠️ ДЕФОЛТ = NoToneMapping, менять ОБЯЗАТЕЛЬНО
renderer.toneMappingExposure = 0.9;
renderer.shadowMap.enabled = true;
renderer.shadowMap.type = THREE.PCFShadowMap;                // НЕ PCFSoft — там radius мёртв, см. п.2
renderer.shadowMap.autoUpdate = false;                       // декорации статичны
// после сборки/морфинга сцены: renderer.shadowMap.needsUpdate = true;

// r160: _useLegacyLights уже false → интенсивности ФИЗИЧЕСКИЕ. 1.0 будет темно.
const sun  = new THREE.DirectionalLight(0xfff0dc, 3.0);
const fill = new THREE.HemisphereLight(0xbfd4ff, 0xb08050, 0.35);
// AmbientLight при наличии scene.environment НЕ НУЖЕН — плоско убивает объём. Если очень надо — 0.1.
// castShadow = true СТРОГО у одного источника. Вторая теневая лампа удваивает цену.
```

### 1. IBL из панорамы — и главный камень 8K

`PMREMGenerator._fromTexture` в r160 выводит размер кубмапа **из ширины панорамы**: `cubeSize = image.width / 4`. Панорама 8192 → cubeSize 2048 → `_lodMax = 11` → сотни МБ и фриз 1.2–2.5 с (на слабой машине — потеря WebGL-контекста). Док-коммент r160 прямо говорит: идеальный вход — 1024×512.

```js
const pmrem = new THREE.PMREMGenerator(renderer);
pmrem.compileEquirectangularShader();   // прогреть ПОКА грузится JPG

function equirectForIBL(image, width = 1024) {
  const c = document.createElement('canvas');
  c.width = width; c.height = width >> 1;
  const g = c.getContext('2d'); g.imageSmoothingQuality = 'high';
  g.drawImage(image, 0, 0, c.width, c.height);
  const t = new THREE.CanvasTexture(c);
  t.mapping    = THREE.EquirectangularReflectionMapping;   // без этого _fromTexture решит, что это кубмап
  t.colorSpace = THREE.SRGBColorSpace;                     // ОБЯЗАТЕЛЬНО для LDR JPG/PNG
  return t;
}

new THREE.TextureLoader().load('/pano/knossos.jpg', (big) => {
  big.colorSpace = THREE.SRGBColorSpace;
  skySphere.material.map = big;                            // 8K на видимую сферу

  const small = equirectForIBL(big.image, 1024);           // 1K на IBL
  const rt = pmrem.fromEquirectangular(small);
  scene.environment = rt.texture;                          // именно .texture
  small.dispose();
  pmrem.dispose();                                         // ТОЛЬКО когда все PMREM построены
});
```

**Разница в 30 раз** по времени старта: ~1500 мс → ~60 мс. На камне/глине с `roughness 0.6–0.9` визуальной разницы между 1024 и 2048 нет вообще.

Ловушки:
- `TextureLoader` **не ставит** `colorSpace`. Забыли `SRGBColorSpace` на JPG → окружение вымытое и пересвеченное.
- `pmrem.dispose()` делает непригодными **все** экземпляры (док-коммент r160). Один генератор на приложение.
- `scene.backgroundBlurriness` работает только если `scene.background` — PMREM-текстура. На вашей 8K-сфере не сделает ничего.

**`scene.environmentIntensity` в r160 НЕ СУЩЕСТВУЕТ** (появилось в r163) — `grep` по билду даёт 0 совпадений. Крутить только по материалам:

```js
function setEnvIntensity(root, k) {
  root.traverse(o => { if (!o.isMesh) return;
    for (const m of (Array.isArray(o.material) ? o.material : [o.material]))
      if ('envMapIntensity' in m) m.envMapIntensity = k;   // needsUpdate не нужен, это uniform
  });
}
```
Рабочие значения: известняк/штукатурка/пол **0.6–0.8** (больше — камень выглядит пластиковым), обожжённая глина **0.8–1.0**, бронза/золото **1.2–1.6** (металлу IBL необходим, иначе он чёрный), дерево **0.5–0.7**.

### 2. Тени

**Главное заблуждение:** `PCFSoftShadowMap` **игнорирует** `shadow.radius`. Проверено по шейдеру r160: в ветке `SHADOWMAP_TYPE_PCF` `shadowRadius` встречается 4 раза, в `SHADOWMAP_TYPE_PCF_SOFT` — **ни разу** (там фиксированное ядро 9 тапов шириной ровно 1 тексель). Берите обычный `PCFShadowMap` — 17 тапов, `radius` работает.

```js
sun.position.set(6, 9, 4);
sun.target.position.set(0, 0, 0);
scene.add(sun, sun.target);
sun.castShadow = true;

const R = 7.0;                        // радиус сцены 6.5 + запас
const s = sun.shadow;
s.mapSize.set(2048, 2048);            // 4096 = удвоение depth-прохода почти ни за что
s.camera.left = -R; s.camera.right = R;
s.camera.top  =  R; s.camera.bottom = -R;
s.camera.near = 1;                    // НЕ 0.5 — сжимайте диапазон
s.camera.far  = 24;
s.camera.updateProjectionMatrix();    // ОБЯЗАТЕЛЬНО после правки границ

// АРИФМЕТИКА BIAS, а не подбор наугад:
// мир на тексель = 2R / mapSize = 14 / 2048 = 0.0068 м = 6.8 мм
s.normalBias = 0.015;                 // ≈2 текселя — убирает акне на цилиндрах и наклонных стенах
s.bias       = -0.0004;               // маленький отрицательный, по модулю не больше 0.001
s.radius     = 3;                     // 2–4 приятная мягкость, >6 начинает бахромить
```
Дефолты r160 для вашей сцены непригодны: `mapSize 512` (мыло) и `far 500` (вся точность глубины уходит в пустоту).

Отладка: полосатое акне на боках пифоса → поднимать **`normalBias`** шагом 0.005, не `bias`. Тень отрывается от подошвы → `normalBias` велик. Лесенка по краю → сначала **сужать** `shadow.camera` до реального радиуса, только потом растить карту. Помогает `scene.add(new THREE.CameraHelper(sun.shadow.camera))` — рамка должна плотно облегать сцену.

⚠️ Три сама переворачивает грани для depth-прохода (`FrontSide → BackSide`). Замкнутые тела (пифос, колонна, блок) самозатеняются корректно, а односторонний `PlaneGeometry`-пол — плохо. **Полу дать толщину `BoxGeometry`.**

### 3. Тонмаппинг

`AgXToneMapping` в r160 **есть** (константа 6, появилась именно в этом релизе).

- **ACESFilmic** — контрастный, тянет тёплое в оранжевый, добавляет насыщенности. Для критского полудня (охра, терракота, известняк) это плюс. Внутри шейдера: `color *= toneMappingExposure / 0.6` — то есть **ACES сам умножает на 1.667**, поэтому `exposure 1.0` у ACES ярче, чем у AgX.
- **AgX** — не выжигает пересветы, держит оттенок у солнца и пламени, но заметно **десатурирует** (вмещает 16.5 стопов: `AgxMinEv -12.47 … AgxMaxEv +4.026`).

Отправные точки (доводить глазом на ваших панорамах):

| сцена | ACES | AgX |
|---|---|---|
| полдень, яркая критская панорама | `exposure 0.85` | `1.30` |
| закат / мегарон Микен с очагом | `1.10–1.25` | `1.60–1.80` |
| тёмная факельная кладовая | — | **`1.90`** (AgX предпочтительнее, пламя не станет белым пятном) |

Если выбрали AgX и не хватает цвета — **не** крутите exposure вверх (получите муть), поднимите насыщенность материалов: `material.color.setHSL(h, s*1.15, l)`.
⚠️ Смена `toneMapping` = рекомпиляция **всех** материалов сцены, фриз 200–800 мс. Делать на инициализации, **никогда в UI-слайдере**.

### 4. Материалы

**`MeshPhysicalMaterial` для камня, глины, штукатурки и дерева не даёт НИЧЕГО, кроме потери кадров.** Он всегда объявляет `defines {STANDARD, PHYSICAL}` → компилируется тяжёлый физический шейдер даже при нулевых фичах: ~10–15% фрагментного времени на пустом месте.

- `clearcoat` — только на **глазурованной** керамике: `clearcoat 0.35`, `clearcoatRoughness 0.25`. На необожжённом пифосе, известняке, штукатурке вредно.
- `sheen` — только ткань/драпировка (`0.4` / `sheenRoughness 0.7`). На камне бесполезен.
- `iridescence` — исторически неуместно, не брать.
- `transmission` — **НИКОГДА**. При `transmission > 0` рендерер каждый кадр заводит `_transmissionRenderTarget`, перерисовывает в него **всю непрозрачную сцену** и строит мипы. Для бронзового века стекла нет.

```js
const limestone = new THREE.MeshStandardMaterial({
  color: 0xc9c0ad,
  roughness: 0.92,        // камень почти не блестит
  metalness: 0.0,         // ⚠️ НЕ 0.5 «на глаз» — это главная ошибка, всё становится грязно-серым
  normalMap: nrm, normalScale: new THREE.Vector2(0.8, 0.8),
  roughnessMap: rgh,      // ВАРИАЦИЯ шероховатости важнее её среднего значения
  aoMap: arm, aoMapIntensity: 1.0,
  envMapIntensity: 0.7
});
const clay   = new THREE.MeshStandardMaterial({ color: 0xa8653f, roughness: 0.78, metalness: 0.0, envMapIntensity: 0.9 });
const bronze = new THREE.MeshStandardMaterial({ color: 0x9c6f3a, roughness: 0.35, metalness: 1.0, envMapIntensity: 1.4 });
```
**Правило: `metalness` строго 0.0 или 1.0.** Промежуточное физически бессмысленно и выглядит как грязь. Реализм на диэлектриках даёт `roughnessMap`, а не `metalness`.

Подключение наших ARM-карт (одна текстура в три слота — сознательно, чтобы влезть в бюджет):
```js
mat.aoMap = mat.roughnessMap = mat.metalnessMap = armTex;
```

**⚠️ Грабли `aoMap` в r160.** Атрибута `uv2` больше нет — есть `uv1` и свойство `texture.channel`.
- Для **процедурной** геометрии (`Cylinder/Lathe/Box`) UV уже нормальные, неперекрывающиеся → просто оставить `armTex.channel = 0` (дефолт), дублировать ничего не надо.
- Для загруженных GLB с отдельной AO-развёрткой → `geometry.setAttribute('uv1', geometry.attributes.uv.clone()); mat.aoMap.channel = 1;`

`aoMap` влияет **только на непрямой свет** (`indirectDiffuse`). Значит: без `scene.environment` его почти не видно (сначала IBL, потом AO), и он **не** затемняет прямое солнце. Хотите тёмные щели и на солнце — умножайте в `map`/`color`.

**Цветовое пространство карт:** `map` и `emissiveMap` → `SRGBColorSpace`. `normalMap`, `roughnessMap`, `aoMap`, `metalnessMap` → **`NoColorSpace`** (дефолт). Случайный sRGB на AO делает его неправдоподобно контрастным.

Глобальный фиксер после каждой загрузки GLB (анизотропия — дефолт **1**, это главная причина «мыла» на полу):
```js
const maxAniso = renderer.capabilities.getMaxAnisotropy();  // обычно 16
function fixTextures(root) {
  root.traverse(o => { if (!o.isMesh) return;
    for (const m of (Array.isArray(o.material) ? o.material : [o.material])) {
      for (const k of ['map','normalMap','roughnessMap','aoMap','metalnessMap','emissiveMap']) {
        const t = m[k]; if (!t) continue;
        t.anisotropy = maxAniso;
        t.colorSpace = (k === 'map' || k === 'emissiveMap') ? THREE.SRGBColorSpace : THREE.NoColorSpace;
        t.needsUpdate = true;
      }
      m.side = THREE.FrontSide;   // у всех камней Poly Haven doubleSided:true — бессмысленно, снимает половину нагрузки
    }
  });
}
```

**Три обязательных патча при загрузке конкретных файлов:**
```js
// 1) hd-pithos.glb, hd-phaistos-disc.glb, hd-oil-lamp2.glb — цвет в вершинах, текстур нет
mat.vertexColors = true;            // иначе серая болванка

// 2) hd-cypriot-bottle.glb, hd-terracotta-lamp.glb — KHR_materials_unlit → не примут свет сцены
mesh.material = new THREE.MeshStandardMaterial({ map: old.map, roughness: 0.85, metalness: 0 });

// 3) камни/деревья Poly Haven: AO лежит в R-канале ARM, но occlusionTexture в glTF НЕ объявлен
mat.aoMap = mat.roughnessMap;
```

### 5. Геометрия

**Сегменты.** Дефолт `LatheGeometry` — `segments = 12` (!), это и есть источник гранёности сосудов. Дефолт `CylinderGeometry` — `radialSegments = 32`.

| объект | сегменты |
|---|---|
| пифос/амфора (`Lathe`) | **64**, профиль из 24–32 точек через `CatmullRomCurve3`, а не ломаной |
| **критская колонна** (`CylinderGeometry(radiusTop 0.28, radiusBottom 0.20, h 2.6, 48, 1)` — сужается **книзу**) | 48 |
| чаша/кубок | 48 |
| факел, ножка стола | 16–24 |

Цена: `Lathe = segments × (points−1) × 2`. 64×30×2 = 3840 тр на сосуд, 20 сосудов = 77k. Нормально.

**Нормали.** Не выбирайте между `computeVertexNormals` (всё мылится) и `flatShading` (цилиндр становится призмой). Третье, правильное:
```js
import { toCreasedNormals } from 'three/addons/utils/BufferGeometryUtils.js';
geo = toCreasedNormals(geo, THREE.MathUtils.degToRad(35));
```
Рабочие углы: камень/блоки **30–40°**, керамика **45–60°**, дерево **25–35°**. ⚠️ Возвращает **неиндексированную** геометрию (вершин втрое больше) — применять на финальной геометрии, **до** `InstancedMesh`, один раз.
`flatShading = true` оставить намеренно для расколотого камня и грубо тёсаных блоков — он **бесплатен**.

**Фаска — самый дешёвый источник «дорогого» вида.** Реальные объекты не имеют математически острых рёбер, фаска ловит блик.
```js
const w = 1.2, h = 0.8;
const shape = new THREE.Shape();
shape.moveTo(-w/2,-h/2); shape.lineTo(w/2,-h/2); shape.lineTo(w/2,h/2); shape.lineTo(-w/2,h/2); shape.closePath();
let geo = new THREE.ExtrudeGeometry(shape, {
  depth: 0.9, bevelEnabled: true,
  bevelThickness: 0.035, bevelSize: 0.030,   // держать примерно равными
  bevelOffset: 0, bevelSegments: 2,          // 2 хватает для камня; 3–4 для керамики
  curveSegments: 6, steps: 1
});
geo.center();
```
Блок с фаской ≈ 90–140 тр, 40 блоков стены ≈ 5k. Копейки.
⚠️ **`bevelEnabled` по умолчанию `true`, а `bevelThickness = 0.2`** — на блоке 1.2 м это фаска в 20 см, объект превратится в подушку. ⚠️ `bevelSize` по умолчанию `= bevelThickness − 0.1`; при `bevelThickness < 0.1` получится **отрицательный** размер и вывернутая геометрия. Всегда задавать оба явно. `ExtrudeGeometry` строит вдоль +Z и выдаёт UV в **мировом** масштабе (тайлинг консистентен между блоками разного размера — это плюс).

**`normalMap` на процедурной геометрии тангенсы НЕ требует.** `Cylinder/Lathe/Extrude/Box` не имеют атрибута `tangent`, и это нормально: r160 строит TBN функцией `getTangentFrame` из экранных производных. `geometry.computeTangents()` вызывать **не нужно** (он требует индексированную геометрию и часто падает).
`normalScale`: **0.6–0.9** известняк/штукатурка/шершавая глина (рабочий диапазон), 0.3–0.5 полировка/глазурь, 1.0 почти всегда перебор и читается как пластик. Если рельеф «наизнанку» — `normalScale.set(1, -1)`.

**`displacementMap` — почти всегда ловушка.** Это чисто вершинный сдвиг вдоль нормали: (1) эффект есть только там, где есть вершины — на `BoxGeometry(1,1,1)` не сделает ничего, для бугристого блока нужна сетка `48,32,36` = ~20k тр на **один** камень; (2) нормали **не** пересчитываются, освещение останется от гладкой формы; (3) соседние объекты разъезжаются по швам.

Вместо него — **неровность геометрией**, 90% эффекта за 2% цены:
```js
const b = new THREE.BoxGeometry(w, h, d, 3, 3, 3);
const p = b.attributes.position;
for (let i = 0; i < p.count; i++)
  p.setXYZ(i, p.getX(i)+(Math.random()-0.5)*0.045,
              p.getY(i)+(Math.random()-0.5)*0.030,
              p.getZ(i)+(Math.random()-0.5)*0.045);
b.computeVertexNormals();
// ~300 тр на блок, 40 блоков = 12k — и глыбы перестают быть кубиками
```
Единственное оправданное применение displacement — земляной пол одним `PlaneGeometry(14,14,128,128)` (~32k тр), `displacementScale 0.06`.

**Subdivision:** в r160 его нет ни в ядре, ни в addons (`SubdivisionModifier` удалён в r125; `TessellateModifier` дробит треугольники, но **не сглаживает форму**). Внешний `three-subdivide@1.1.5` (MIT, peerDep three ≥0.125) подключается строкой в importmap. **Скорее не нужен:** одна итерация = ×4 треугольников. Для тел вращения поднять `segments` у `Lathe/Cylinder` до 64 дешевле и точнее, чем субдивайдить куб.

### 6. Циклопическая кладка Микен — рецепт

Циклопическая кладка — это буквально «огромные необработанные валуны, плотно подогнанные насухо, без рядов и раствора». Готовой модели под CC0/CC-BY не существует (проверено, см. ниже). Собирать кодом из наших пяти сканов:

```js
// InstancedMesh из hd-rock-boulder-arid-03 / arid-06 / boulders-group / rock-07 / rock-09
// случайный поворот по Y, scale.y ≈ 0.6–0.8 (сплющить), укладка в 3–4 НЕРОВНЫХ яруса со смещением,
// плотная подгонка встык. Мелочь у подножия — hd-stone-rubble-scatter + hd-stone-gravel-scatter:
// именно она продаёт «руину» глазу.
```
Готовый набор в бюджет 400k: `fort-modular 28k + arid-03 65k + arid-06 109k + boulders-group 41k + rock-face-02 30k + rock-07 15k + rock-09 12k + rubble-scatter 86k = 386 000 тр.`

⚠️ **Геологическая честность:** сканы сняты в Намакваленде (ЮАР) — это гранит/кварцит/песчаник, а Микены и Кносс сложены **серым известняком**. Тонировать `material.color` в холодный серо-бежевый `0xb8b0a2` — снимает рыжину.

### 7. Процедурные normal/roughness для колонны и ступеней

Три шага: тайлящийся fBm-height → Sobel в normal → та же высота в roughness. Полный код (`fbm`, `normalTex`, `roughTex`) лежит в исходном ресёрче; главное — параметры и оба обязательных свойства текстуры:

```js
t.wrapS = t.wrapT = THREE.RepeatWrapping;
t.colorSpace = THREE.NoColorSpace;                        // ДАННЫЕ, не цвет
t.anisotropy = renderer.capabilities.getMaxAnisotropy();  // дефолт 1 — без этого камень замылится вдаль
```

| материал | fBm | strength | normalScale | roughness lo/hi | repeat |
|---|---|---|---|---|---|
| известняк (блоки Микен) | `octaves 6, base 6, gain 0.55` | 3.0 | 0.9 | 0.95 / 0.80 | (2,2) + 30–50 тёмных каверн r=2–6 px перед Sobel |
| штукатурка (стена под фреску) | `octaves 4, base 14, gain 0.45` | 1.4 | 0.45 | 0.90 / 0.75 | (3,3) |
| обожжённая глина (пифос) | `octaves 5, base 20, gain 0.5` | 1.1 | 0.5 | 0.85 / 0.68 | **(1,3)** вертикально + отдельно нарисовать горизонтальные полосы гончарного круга |

Генерация 1024² с 5 октавами ≈ 60–120 мс на главном потоке. Если карт 4+, вставлять `await new Promise(r=>setTimeout(r))` между ними, иначе видимый фриз.

### 8. Цена приёмов (оценки из подсчёта тапов/проходов в r160, не замеры)

Разово, на загрузке: PMREM с 1024×512 — **40–80 мс**, с 8192 — **1200–2500 мс** (разница в 30 раз, пункт №1 по важности). Процедурная карта 1024² — 60–120 мс. `toCreasedNormals` на 50k — ~80 мс.

Каждый кадр: IBL **+6–10%** (лучшее соотношение во всём списке, берём безусловно) · тонмаппинг **+1–2%** · тени PCF 2048² с `autoUpdate=false` **+10–14%** · VSM **+18–28%** (дорого) · `MeshPhysical` при нулевых фичах **+8–15% ни за что** · `clearcoat` +10–15% · **`transmission` +60–100%** · normal+rough+ao суммарно **+4–7%** · анизотропия ×16 **+1–3%**.

Рекомендуемый набор: IBL(1K) + ACES/AgX + **одна** тень PCF 2048 с `autoUpdate=false` + Standard-материалы + max anisotropy ≈ **+30–40%** к пустому кадру, укладывается в 60 fps.

## Порядок работ

Отсортировано по приросту реализма на единицу труда. После шага **4** руководитель уже увидит разницу; шаги 8–11 — доводка.

1. **Стартовый блок рендерера** (п.0): `toneMapping = ACESFilmic`, `exposure 0.9`, `setPixelRatio ≤ 2`, физические интенсивности света (`sun 3.0`, а не 1.0), убрать `AmbientLight`. **5 минут, самая большая разница во всём списке.**
2. **IBL с даунскейлом панорамы до 1024×512** (п.1). Без него ничего из PBR не работает как задумано, а с 8K-входом сцена фризит на 1.5–2.5 с. 10 минут.
3. **`fixTextures()` на каждой загрузке GLB** (п.4): анизотропия ×16, правильные colorSpace, `side = FrontSide`. Одна функция, снимает «мыло» на полу и стенах.

### Три предупреждения по пайплайну

- ⚠️ **Не гонять `glb-shrink-tex.mjs` с `maxPx < 1024` по файлам с листвой** — скрипт безусловно перекодирует в JPEG, а JPEG теряет альфу, вырезание умрёт **молча** и листва снова станет сплошными прямоугольниками. С `maxPx = 1024` безопасно (альфа-PNG уже 1024, скрипт его пропускает).
- ⚠️ **Не упрощать листву meshopt-ом** — она из тысяч несвязных островов, edge-collapse схлопывает их в ничто (первый прогон дал голые деревья). Прореживать островами: выкинуть часть листьев целиком, оставшиеся увеличить вокруг центроида.
- ⚠️ **Не терять `KHR_texture_transform`** при любой перепаковке `hd-olive-*.glb` — он в `extensionsRequired`, без него `GLTFLoader` откажется грузить файл.

**Бюджет текстур выедается оливами:** одна `hd-olive-*.glb` несёт 9 карт (8×2048²) — почти вся квота «10 текстур 2048² на сцену». Одна олива-герой в полном разрешении, остальные — `-lite` или инстансы того же файла. По треугольникам две оливы = 295k из 400k, третье дерево уже не влезет; `hd-cypress` (744 тр) и `hd-aleppo-pine` (584 тр) не считаются вовсе.
